三種編號，各有用途（最重要）Three numbers, three jobs (most important)

系統內有三種編號，用途各不相同，切勿混用。對單時，先看「專案編號」確認是哪一個客人的個案，再看「發票編號」確認是哪一次付款。There are three distinct numbers — never mix them up. When reconciling, use the project number to identify the customer's case, then the invoice number to identify a specific payment.

一單「安排預約接送」如何流動How one pick-up booking flows

  1. 客人在網站「安排預約接送」頁填寫資料，並繳付 HK$1,800 訂金。首次預約時，系統自動產生專案編號 RSL-…；回訪客人可填回原有編號。The customer fills the pick-up booking page and pays a HK$1,800 deposit. A project number RSL-… is generated on a first booking; returning clients can enter theirs.
  2. 資料經伺服器寫入 Supabase（狀態：待付款），並附上付款參考 PAY-…。The server saves it to Supabase (pending) with a payment reference PAY-….
  3. 客人跳轉至 Shopify 結帳付款，Shopify 產生發票編號（Shopify 訂單號）。They pay on Shopify checkout; Shopify issues the invoice (order) number.
  4. 付款成功後，Shopify 自動通知網站（webhook），以付款參考對回該筆記錄，標記為已付款，並補上發票編號與金額。On success, a webhook matches the payment reference, marks the record paid, and adds the invoice number and amount.
  5. 你在後台「接送服務」看到已付款預約，安排接送；其後的火化預約與紀念品沿用同一個專案編號。You see it under Pick-up services and arrange collection; later cremation and keepsakes reuse the same project number.

  1. 用瀏覽器開啟 github.com/Resoul-Design/Resoul-landing，並確認已登入客戶 GitHub 帳戶。Open the repo and make sure you are signed in.
  2. 在檔案列表按要修改的檔案。常用：index.html（首頁）、about.html（關於我們）、cremation.html（火化善終旅程）、euthanasia.html（上門安樂死）、booking.html（安排預約接送）、pricing.html（服務收費，已隱藏）、support.html（情緒支援）、board.html（主人評價及故事分享）、reviews.html（Google 評價）、referral.html（專業輔導轉介及資源）。Click the file to edit (home / about / cremation farewell journey / at-home vet assessment & euthanasia / pick-up booking / pricing / emotional support / owner reviews & stories / Google reviews / counselling referral & resources).

十一、常見問題排解Troubleshooting

後台登入不到／按登入沒有反應Can't log in

  • 確認使用的是 resoul-admin-five.vercel.app，而非一串亂碼的部署網址。Use the main URL, not a hashed deploy URL.
  • 密碼錯誤 → Supabase → Authentication → Users 重設密碼。Wrong password → reset it in Supabase.
  • 完全沒有反應 → 多數是 Vercel 環境變數缺失，或已修改但未 Redeploy。No reaction → usually a missing env var or a change not redeployed.

已付款但預約仍顯示「待付款」Paid but still "pending"

  • 檢查 Landing 的 Vercel 已設 SUPABASE_URL、SUPABASE_SERVICE_ROLE_KEY、SHOPIFY_WEBHOOK_SECRET 並已 Redeploy。Check landing env vars are set and redeployed.
  • 確認 Shopify「訂單付款 (orders/paid)」webhook 指向 Landing /api/shopify-webhook，簽署密鑰一致。已完成的舊訂單不會自動重試。Confirm the orders/paid webhook points to Landing /api/shopify-webhook with a matching secret; past orders won't retry.

修改後網站沒有更新Site not updating

  • 確認已 Commit；確認 Vercel Deployments 顯示 Ready；按 Ctrl + Shift + R；記得中英文是兩個檔案。Confirm commit + Ready deploy; hard refresh; both language files.

故事分享頁看不到客人的貼文Memorial post not showing

  • 故事分享頁貼文預設「顯示中」，不在「待審」分頁，請按「顯示中」或「全部」。Posts default to Visible — check "Visible" or "All".
  • 若客人選了「只限連結」，故事不會在故事分享頁公開列出，只可經專屬連結瀏覽（見下方「客人忘記只限連結故事的網址」）。If the customer chose Link-only, the story isn't listed on the sharing page and is viewable only via its private link (see "A customer forgot their link-only story address" below).

AI 傾聽對話／寫信沒有回應AI chat / letter not responding

  • 多數是 Landing 未設 GEMINI_API_KEY（或已設但未 Redeploy）。未設時系統仍可用，但只會以預設離線內容回覆。Usually GEMINI_API_KEY is not set on Landing (or set but not redeployed). Without it, the tools still work but only return built-in offline responses.

付款頁顯示「商品不存在」Checkout shows 'product does not exist'

  • 「預約接送訂金」或火化方案被設為草稿，或未發佈到「Headless」管道。到 Shopify → Products 把該產品設為 Active 並發佈到 Headless 管道。The deposit or plan product is Draft or not on the Headless channel; set it Active and publish to Headless.

  • 回訪客人填寫的「已有專案編號」必須以 RSL- 開頭；格式不符時系統會提示。新客人留空即可，系統會自動產生。A returning client's project number must start with RSL-; new clients leave it blank and one is generated.
  • 如表單回覆 503（security_service_unavailable），多數是 Supabase 未建立防濫用函數 consume_api_quota（public_api_security.sql），或 Landing 缺 SUPABASE_URL／SUPABASE_SERVICE_ROLE_KEY。A 503 (security_service_unavailable) usually means the abuse-prevention function consume_api_quota (public_api_security.sql) is missing in Supabase, or Landing lacks SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEY.

專案編號顯示「—」Project number shows "—"

  • 該記錄未有 RSL- 專案編號（多為舊制記錄）。系統不會以 Shopify 訂單號、付款參考或資料列編號代替。可在「火化預約 → 操作 → 編輯資料」的「RSL 專案編號」欄手動填入（只接受 RSL- 開頭的格式）。The record has no RSL- number (usually an older record). 後台載入緩慢Admin feels slow

  • 後台伺服器須與 Supabase 資料庫在同一地區：資料庫在首爾（ap-northeast-2），後台 vercel.json 已設定 "regions": ["icn1"]（Vercel 首爾）。如日後把 Supabase 搬到其他地區，須同步修改此設定，否則每次查詢都要跨區，後台會明顯變慢。The admin's server functions must run in the same region as the Supabase database: the database is in Seoul (ap-northeast-2) and the admin's vercel.json sets "regions": ["icn1"] (Vercel Seoul). If Supabase is ever moved, update this setting too, or every query crosses regions and the admin becomes noticeably slow.
  • 確認方法：在瀏覽器開發者工具查看回應標頭 x-vercel-id，中間一段應為 icn1。紀念品訂單的 Shopify 產品目錄會快取 5 分鐘，新上架產品最多 5 分鐘後才出現在「新增訂單」。To check: the x-vercel-id response header should contain icn1 in the middle. The Shopify product catalog for new souvenir orders is cached for 5 minutes, so newly listed products can take up to 5 minutes to appear.

網站已更新，但手機或電腦仍見舊版Site updated but a phone or computer still shows the old version

十二、安全提醒Security notes

  • service_role key 擁有最高權限，只可放在 Vercel 後端環境變數，切勿放入網頁、GitHub 或傳送給他人。The service_role key is all-powerful; keep it only in Vercel backend env vars.

13 / Data sync

十三、資料同步（Shopify · Supabase · Admin）Data sync

三個系統各有分工，靠 webhook（自動）與同步按鈕（手動）連接。理解邊個係「真相來源」，就知道應該喺邊度改資料。Three systems connected by webhooks (automatic) and a sync button (manual). Know the source of truth to know where to edit.

  • Shopify＝產品、價錢、結帳、付款與發票編號（Shopify 訂單號）的真相來源。Shopify = source of truth for products, prices, checkout, payment and invoice numbers.
  • Supabase＝資料庫，是接送訂金、火化預約、獸醫評估及內部資料（留言、員工、專案收支、審計）的真相來源，並存放產品訂單副本；專案編號（RSL-…）亦存於此。Supabase = database; source of truth for deposits, cremation bookings, vet assessments and internal data, plus the RSL- project number; holds a copy of product orders.
  • Admin＝操作介面，讀寫 Supabase、讀取 Shopify，本身不存數據。Admin = interface; reads/writes Supabase and reads Shopify.

預約與付款（自動）Booking & payment (automatic)

  1. 客人提交「安排預約接送」或火化表單 → 伺服器 API 寫入 Supabase（待付款），附上專案編號 RSL-… 與付款參考 PAY-…。The form → server API writes a pending record with the RSL- project number and PAY- payment reference.
  2. 客人跳往 Shopify 結帳付款 → Shopify 產生發票編號。Shopify checkout → Shopify issues the invoice number.
  3. orders/paid webhook → 以付款參考對回 Supabase 的接送訂金或火化記錄 → 標「已付款」並補上發票編號與金額。orders/paid webhook matches the payment reference to the deposit or cremation record → marks it paid with the invoice number and amount.
  4. Admin 讀 Supabase 顯示；收入自動計入專案；同一客人其後的服務沿用同一個專案編號。Admin shows it; paid amounts auto-count as income; later services reuse the same project number.

產品訂單、取消與退款Product orders, cancel & refund

  • 產品訂單：Shopify 落單 → webhook 或「同步 Shopify 訂單」按鈕存入 Supabase → Admin「客戶訂單」顯示。Product orders: webhook or the Sync button stores them in Supabase.
  • 取消／退款：orders/updated webhook 自動把火化預約標「已取消／已退款」、更新產品訂單；已取消收入歸 $0。orders/updated flips cancel/refund; cancelled income = $0.
方向性 DIRECTIONAdmin 改「火化預約」只寫 Supabase，不會回寫 Shopify。「產品訂單」在 Admin 是唯讀副本，要修改請到 Shopify。原則：產品去 Shopify 改；火化預約在 Admin 改。Editing a booking writes only to Supabase; product orders are read-only here (edit in Shopify). Rule: products in Shopify, bookings in the admin.

15 / Glossary

十五、名詞解釋Glossary

  • Webhook：Shopify 在事件（付款、更新）發生時自動通知網站，用來即時同步。Shopify auto-notifies the site on events for real-time sync.
  • Commit / Deploy / Redeploy：GitHub 儲存＝Commit；Vercel 自動發佈＝Deploy；改環境變數後要手動 Redeploy。Save on GitHub = Commit; Vercel publishes = Deploy; after env changes, Redeploy.
  • 環境變數／密鑰：連接各系統的「鑰匙」，設在 Vercel，屬機密。The keys connecting systems, set in Vercel; confidential.
  • 銷售管道（Headless）：Shopify 產品要「發佈」到某銷售管道才對外可買；本店付款用「Headless」管道。A product must be published to a channel to be buyable; checkout uses 'Headless'.
  • Draft / Active：Shopify 產品狀態；Draft＝草稿（不可買），Active＝上架。Draft = not buyable; Active = live.
  • 專案編號（RSL-…）：同一客人整個善終旅程共用的個案編號，首次預約時產生，接送、火化、紀念品都沿用。Project no. (RSL-…): one case number shared across a customer's whole journey, created at the first booking.
  • 付款參考（PAY-…，payment_ref）：每次付款產生，用來把 Shopify 付款對回 Supabase 記錄；只作系統核對。Payment ref. (PAY-…): created per payment to match a Shopify payment to its record; internal only.
  • 發票編號（Shopify 訂單號）：每次在 Shopify 付款時產生的正式收費單據編號；每次付款各一個，可與專案編號不同。Invoice no. (Shopify order no.): the formal bill number, one per payment; can differ from the project number.
  • 獸醫評估 vs 火化預約：「上門安樂死」的查詢，與火化預約分開檢視及統計。Vet assessments are at-home vet assessment & euthanasia enquiries, viewed and counted separately from cremation bookings.
  • 只限連結／分享連結：故事不公開列出，只有持 ?s=… 專屬連結者可瀏覽；後台可複製連結。Link-only / share link: a story not listed publicly, viewable only via its private ?s=… link; the admin can copy it.
  • 限流（防濫用）：每個網絡在一定時間內可使用公開表單及 AI 功能的次數上限。Rate limit: a cap on how often one network can use public forms and AI tools within a time window.
